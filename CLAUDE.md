## Absolute Rules (Non-Negotiable)

### TypeScript
- Strict mode always. No `any`. No `// @ts-ignore`. Refactor the type, don't suppress it.
- Explicit return types on every function.
- All async operations handle errors — no silent failures.
- No `console.log`. Use Pino on backend, structured `console` with context on frontend.

### Database
- Every table has `organization_id`. No exceptions. Multi-tenancy is structural, not bolted on.
- All queries scoped by `organization_id`. Use helpers in `packages/shared` to enforce this.
- Migrations first — `drizzle-kit generate` then `drizzle-kit migrate`. Never hand-edit schema.
- Seed data only in `seeds/`, loaded only in `NODE_ENV=development`.

### API
- Every endpoint validates input with Zod. Invalid input = `400` with clear message.
- Every endpoint verifies auth (API key or session). Missing/invalid = `401`.
- Rate limiting on every endpoint via `@fastify/rate-limit`. Ingestion stricter than reads.
- Standard error shape: `{ code, message, details?, timestamp }`.
- State-changing operations accept optional `idempotency_key`. Store in DB.

### External APIs (LLM, Embeddings, Cohere)
- Exponential backoff, max 3 retries, configurable timeout (10s embeddings, 30s LLM).
- Log every LLM and embedding call: model, tokens, cost. Store in DB.
- No hardcoded secrets. Environment variables only. Fail fast on boot if missing.
- Default 30s timeout for all external calls.

### Prompts
- All prompts live in `backend/src/prompts.ts`. Every prompt has a version number.
- Never scatter prompts across files.
- When prompts change, bump the version and note the change in CHANGELOG.md.

### LLM / Anthropic SDK
- Use `claude-sonnet-4-6` as default model unless task requires otherwise.
- Use prompt caching (`cache_control`) on system prompts and large context blocks.
- Always stream responses for the `/api/ask` endpoint — non-negotiable for UX.
- Track token usage per request. Store `input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_write_tokens`.
- Wrap the Anthropic client in `backend/src/services/llm.ts`. Never import the SDK directly in route handlers.

### Frontend
- No prop drilling. TanStack Query + context for shared state.
- Every async op has: idle, loading, error, success states.
- Semantic HTML. Keyboard navigable. Don't break shadcn/ui accessibility.
- No inline styles. Tailwind only. Dynamic styles via `cn()` utility.
- Frontend Zod schemas mirror backend schemas — share via `packages/shared`.

### Testing
- Integration tests for critical paths: ingest → retrieve → answer.
- No unit tests for simple getters/setters.
- Evals run on every deploy via CI. Regression in retrieval = broken build.

### Git
- Conventional commits: `feat:`, `fix:`, `chore:`, `docs:`, `test:`.
- Branch naming: `feat/feature-name`, `fix/issue-name`.
- CI on every PR: typecheck, lint, build, test. No merge without passing CI.
- CHANGELOG.md updated per release.

## Phased Build Plan

### Phase 1 — Foundation (Week 1–2)
**Goal:** Customer pastes docs URL, asks question, gets streamed answer with citations.

- Monorepo: `backend/`, `frontend/`, `packages/shared/`
- Fastify: health check, Pino logging, error middleware, rate limiting
- Schema: `organizations`, `documents`, `chunks` (vector column), `queries`, `query_chunks`
- Ingestion: URL → scrape (Readability/Cheerio) → chunk → embed (Voyage) → pgvector
- `POST /api/ask`: auth → embed question → vector search → Claude → SSE stream + citations
- React chat page: input, streaming answer, citation cards, loading/error states
- Deploy: Railway (backend) + Vercel (frontend)
- CI: typecheck + lint + build + one integration test

**Do not build:** Multi-tenancy, billing, integrations, admin panel, evals UI.

### Phase 2 — Multi-tenancy + Evals (Week 3)
**Goal:** Onboard 2–3 design partners safely. Know when retrieval breaks.

- `organization_id` on every table. All queries org-scoped. Row-level security.
- API key model: per-org keys, hashed in DB.
- Admin dashboard: orgs, users, ingestion status, recent queries.
- Eval system: `evals` table, CLI runner, 50 seed questions from first design partner.
- Evals run in CI — regression = failing build.

### Phase 3 — Hybrid Search + Reranking (Week 4)
**Goal:** Good enough to charge for.

- Postgres full-text (`tsvector`) + vector search combined via Reciprocal Rank Fusion.
- Cohere reranker as final stage before LLM.
- "I don't know" path: confidence threshold + explicit prompt.
- Multi-turn conversation with context window management.
- Query rewriting before retrieval.
- Eval set grows to 150+ questions. p95 latency < 4s.

### Phase 4 — Intercom Integration (Week 5–6)
**Goal:** Design partner uses RAG inside their actual support workflow.

- Intercom OAuth, encrypted token storage.
- Webhook listener for new conversations.
- Historical ticket import (BullMQ background job).
- "Draft reply" button via Intercom Canvas Kit.
- Human-in-the-loop only — no auto-send.
- Feedback: thumbs up/down → flows into evals.

### Phase 5 — Billing + Self-Serve (Week 7–8)
- Stripe: subscription + usage-based component.
- Self-serve onboarding: signup → connect → first query in 5 min.
- Usage dashboard for customers.
- Customer-facing API docs.

### Phase 6 — Auto-Resolve + Zendesk/Slack (Week 9–12)
- Confidence scoring for auto-send.
- Escalation rules.
- Zendesk + Slack integrations.
- Deflection rate analytics.

## How Claude Code Should Work on This Project

### Do this
1. Ask for the spec first: "What's the input/output? What should it throw on error?"
2. Build vertical slices — `POST /api/ingest` end-to-end, not just the chunker.
3. Write the integration test before moving to the next feature.
4. Org-scope every query. Every mutation verifies org ownership.
5. Log what matters: latency, cost, errors, `org_id`. Structured, searchable.
6. Handle errors first — network timeout, invalid input, rate limit, quota exceeded.
7. Show the implementation before shipping: "Here's how I'm chunking and storing. Review?"

### Don't do this
- Don't build two features in one session. Retrieval is a separate session from ingestion.
- Don't guess at retrieval design — ask before implementing.
- Don't skip retry logic. "I'll add it later" means it never ships.
- Don't hardcode values. Magic numbers go in `config.ts` or `.env`.
- Don't write unit tests for simple functions. Integration tests only.
- Don't scope-creep. "Should I also add webhooks?" — no. Stick to the phase.
